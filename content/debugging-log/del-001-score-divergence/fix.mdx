# The Fix

Two-part fix. Both parts are required — applying only one fails.

<Invariant>
The registered schema must reflect what real scoring data looks like, including NaN-bearing columns. For count-style features that are nullable at scoring time, register as `double`, not `long`. Then the scoring pipeline never needs dtype-branching logic — it just hands a `float64` DataFrame to pyfunc and lets the booster do its job.
</Invariant>

## Part 1 — Re-register the model with all-double schema

<CodeSnippet
  title="Sample input prep — corrected"
  language="python"
  file="utils/del_001_sample_input.py"
>
```python
# All 32 features go to DOUBLE_COLS — no LONG_COLS for nullable counts
LONG_COLS = []
DOUBLE_COLS = FEATURE_COLS  # all 32

assert len(FEATURE_COLS) == 32
assert len(LONG_COLS) + len(DOUBLE_COLS) == 32

# Cast everything to float64, preserving NaN
for col in FEATURE_COLS:
    sample[col] = pd.to_numeric(sample[col], errors="coerce").astype("float64")

# No fillna(0). NaN must reach the booster so the learned default direction is used.
# infer_signature will now read float64 dtypes and emit a schema with 32 "double" entries.
```
</CodeSnippet>

## Part 2 — Simplify `_get_feature_columns` in scoring pipeline

The previous implementation read the schema and branched on dtype. With an all-double schema, no branching is needed.

<CodeSnippet
  title="scoring.py — _get_feature_columns final"
  language="python"
  file="src/pipelines/del_001/scoring.py"
>
```python
def _get_feature_columns(self, pdf: pd.DataFrame) -> pd.DataFrame:
    """
    Cast feature columns to float64, preserving NaN for LightGBM's
    learned default-direction routing.

    With the registered schema set to `double` for all features,
    no dtype-branching is required. A single cast is sufficient.
    """
    try:
        for col_name in pdf.columns:
            pdf[col_name] = pd.to_numeric(pdf[col_name], errors="coerce").astype("float64")
        self.logger.info("Feature type casting complete")
        return pdf
    except Exception:
        self.logger.exception("Error during feature type casting")
        raise
```
</CodeSnippet>

## What this fix means for future model registrations

<Callout type="warning" title="Registration policy">
For any model where a feature column can legitimately be NaN at scoring time (counts for inactive customers, ratios with zero denominators, aggregates over empty windows) — **register the column as `double` in the schema**, regardless of how the training-data dtype looks. The int-vs-float distinction is meaningless to LightGBM/XGBoost/CatBoost at inference time; what matters is whether NaN can pass through to the booster.
</Callout>
