## Replay this case on a new model

If you're investigating a parallel-run divergence on a different model and want to follow the same path:

<Steps>
  <Step title="Get the divergence count and direction">
    How many customers diverge? Is it bidirectional or unidirectional? Unidirectional + population-specific = deterministic code-path bug.
  </Step>

  <Step title="Profile the diverging population">
    What do those customers have in common? Demographic, behavioural, data-shape (lots of NaN? Lots of zeros? Edge-case values?). This profile is your strongest clue.
  </Step>

  <Step title="Build the keyed preprocessing comparison notebook">
    Use the template from this debug — load both MLOps and SME preprocessed parquets, align on customer_id, diff every feature. Eliminates preprocessing as a suspect (or finds the bug) in one shot.
  </Step>

  <Step title="If preprocessing is identical, look at scoring">
    Specifically: how is the model loaded? `mlflow.pyfunc.load_model` enables schema enforcement; `mlflow.{flavor}.load_model` does not. SME usually uses the flavor loader; MLOps usually uses pyfunc. Check the registered schema with `model.metadata.get_input_schema()`.
  </Step>

  <Step title="Compare schema dtypes against actual scoring data dtypes">
    Any column where schema says `long` and scoring data has NaN — that's the bug.
  </Step>

  <Step title="Fix at the contract layer, not the workaround layer">
    Re-register the model with corrected schema. Don't try to silence the pyfunc error with type casts in the scoring code — that path leads to "the fix becomes the bug".
  </Step>
</Steps>

## Related context

- The SME notebook framework calls `mlflow.models.infer_signature(sample, model_output=...)` to build the schema. Schema dtypes come **directly from the pandas dtypes of the sample**. If your sample-prep notebook casts a column to int64, the registered schema gets `long` for that column. This is where the bug enters the system.

- `pd.qcut(...).rank(method='first')` is used for decile ranking in both SME and MLOps. `method='first'` is documented as "ranks assigned in order they appear in the array" — i.e. tie-break by row order. Since Spark doesn't guarantee row order on parquet reads, two runs of the same code can produce different rank assignments for tied customers. Acceptable parallel-run tolerance for most use cases; if exact reproducibility is required, add a deterministic secondary sort.

- The MLOps preprocessing pipeline includes a function literally named `_impute_missing_zero` that does not impute anything — only drops columns above missingness/zero-rate thresholds. The SME version has the same misleading name. Worth renaming in both codebases when the opportunity arises.
